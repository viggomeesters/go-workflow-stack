# v0.3.15 — opt-in execution contracts

Tasks can persist an explicit model/effort and release intent, inherit project
defaults and retain overrides through structured intake. Invalid profiles and
dependency graphs are rejected before task creation writes. Dependency-aware
selection and claim require predecessor completion and, when requested, a bound
release receipt. Typed phase and verification evidence distinguish missing,
failed, non-applicable and successful checks.

This increment establishes contracts. It does not yet launch the selected model,
create task worktrees or publish task releases automatically. Legacy tasks and
historical records retain their existing behavior. Subsequent ABC tasks implement
those runtime capabilities. See `docs/task-release-contract.md` for configuration,
compatibility rules and the limits of declared evidence.

The release also includes previously committed claim-base and remote delivery-SHA
attestation improvements listed in the changelog.

Verification must include the new contract tests, existing smoke/architecture
suite, template pairing, distribution checks and the Linux release validator.
Record exact results in `.go` before publication; this document itself does not
assert those checks passed.

Rollout is opt-in through task `execution_contract` or project
`execution_defaults`. To roll back runtime behavior, return consumers to the
previous immutable runtime pin while preserving task/evidence data. Do not rewrite
published tags or invent release receipts for historical tasks.
