# v0.3.26 — ordered task releases and phase-aware critic

Two dependent tasks can use different explicit model/effort profiles and deliver
separate verified releases. The reproducible campaign exercises actual managed
workers, current verification, rejected-critic repair, local Git publication,
remote readback and cleanup. The second task cannot start before the first release.

A real v0.3.25 trial found a circular pre-publication critic demand for a release
receipt. Managed critics now evaluate the prepared candidate and leave downstream
shipping evidence pending. Missing current checks or unsafe readiness still block;
manual critics and the hard publication/completion gates retain their contracts.
A second live trial exposed worker instructions requiring out-of-sandbox canonical
outcome writes. Task-worktree workers now report evidence; the controller validates
and persists outcomes. Legacy in-place recording is preserved.

The local failure matrix reuses actual tests for stale state, proof completeness,
conflicting bases, surviving workers, interrupted effects, publication/deployment
readback and cleanup retry. A worktree is not a security or test-environment sandbox.

Live result: PENDING_LIVE_PROOF. Requested profiles, raw native results and runtime
source hashes are recorded separately from fixture coverage. Effective model
identity and provider billing remain unconfirmed. Local bare remotes do not claim
hosted deployment access. No GitHub Actions or production deployment is used.

Verification: campaign and relevant regressions, ordinary-clone checks and Linux
candidate/exact-tag distribution gates with immutable template pairing.

Rollback: retain task state/evidence and use explicit supported resume. If the
runtime needs correction, publish a new immutable version; never replace published
tags or rerun confirmed publication during cleanup recovery.
