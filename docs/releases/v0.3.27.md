# v0.3.27 — legacy task metadata compatibility

Fixes the v0.3.26 upgrade regression that rejected valid historical dependency
strings as malformed lifecycle objects. Runtime validation and the published task
schema now honor the existing explicit `execution_contract` opt-in boundary for
dependencies and verification metadata. Reading or upgrading a repository leaves
its task bytes unchanged.

The repair also covers a new task depending on a legacy task: historical metadata
is not traversed as lifecycle edges, while predecessor status and explicitly
required release receipts remain enforced. Explicit intake stays strict. Lifecycle
adoption rejects ambiguous metadata with the task path before any document writes.

A private consumer snapshot with 156 tasks reproduced 33 dependency errors under
v0.3.26 and none under the repaired runtime; all task hashes stayed unchanged.
Only anonymized counts are published. The active consumer repository is untouched.

Verification includes synthetic legacy upgrade/rollback, all task states, schema
parity, strict intake, historical adoption preservation, relevant ABC regressions,
smoke checks and candidate/tagged Linux distribution checks. Template pairing uses
immutable v0.3.16 commit 06678be4fdc95dc671d6adbc1a50b3f073d66b5c.

Rollback: retain task state and the stack-update rollback record. Restore the
previous pin through the guarded rollback API if needed; v0.3.26 still contains
this legacy validation regression. Never rewrite historical dependencies to work
around a runtime bug or replace published tags.
